# BHZD RAG 资料生成、收集与整理规则

## 1. 文档目的

本规则用于指导人员或 AI 生成、收集、清洗、整理和验收可导入 BHZD RAG 系统的文本资料。目标不是单纯增加文件数量，而是建立一批来源可追溯、内容可核验、切片后仍能独立表达、能够稳定回答真实问题的知识资料。

本规则只接受以下正文文件：

- `.md`：首选格式，适合有明确章节、表格、代码或引用的资料。
- `.txt`：适合纯文本资料，但仍须使用本规则规定的 YAML 元数据头和 Markdown 风格标题。

除特别注明外，本文中的“必须”“禁止”属于验收硬门槛，“应”属于默认要求，“建议”可根据资料类型调整。

## 2. 当前系统兼容边界

### 2.1 两种入库方式

| 入库方式 | 可使用的本规则格式 | 文件内 YAML 元数据的作用 | 注意事项 |
| --- | --- | --- | --- |
| 管理端单文件或文件夹上传 | `.md`、`.txt` | 解析时从向量正文中排除，便于文件自身治理 | 数据库中的标题、来源、授权、可见范围等仍以上传界面填写的元数据为准 |
| 本地受控资料包导入 | `.md` | 同时作为资料包导入元数据 | 只读取 `docs/ragData/materials/*.md` 和 `docs/ragData/sources/SRC-*.md`，不读取 `.txt` |

因此：

- 需要通过管理端批量选择文件时，可混合使用合格的 `.md` 与 `.txt`，一次最多选择 1000 个文件。
- 需要构建仓库内受控资料包时，正文和来源台账必须使用 `.md`。
- 文件内元数据不能替代管理端上传表单。批量上传使用同一组表单元数据时，必须保证该批文件确实具有相同来源类型、授权状态、可见范围和数据类型。

### 2.2 解析与切片行为

当前系统对 `.md` 和 `.txt` 使用相同的文本解析逻辑：

1. 文件按 UTF-8 解码。
2. 如果剥离可选 BOM 后的逻辑第一行是 `---` 且存在闭合的 `---`，两行之间的 YAML 元数据不会进入向量正文。
3. 行首的 `# ` 至 `###### ` 被识别为章节标题；标题开启新的语义块。
4. 默认切片长度为 500 字符，重叠为 80 字符，并在切片正文前继承当前章节标题。
5. 当前解析器只保留“最近一个标题”，不自动组合完整的多级标题路径。
6. Markdown 管道表格默认作为原子内容保留，可能形成超过默认长度的单个切片。

资料编写必须适应以上行为，不得假设系统会自动理解目录层级、补全上文、识别附件或纠正错误编码。

### 2.3 系统字段取值

资料元数据应使用以下系统兼容值：

| 字段 | 允许值 | 说明 |
| --- | --- | --- |
| `source_type` | `textbook`、`standard`、`enterprise`、`teacher`、`competition`、`other` | 来源类别 |
| `license_status` | `authorized`、`internal`、`pending`、`forbidden` | 授权状态 |
| `visibility` | `admin`、`teacher`、`student` | 可见范围 |
| `data_types` | 本规则固定为 `text` | 表示正文知识类型，不表示文件扩展名 |

`pending` 或 `forbidden` 资料不得作为已授权学生资料发布。授权、隐私或事实核验未完成时，应保留为待处理资料，而不是降低验收标准直接入库。

## 3. 一份资料的基本单位

### 3.1 单文档单主题

每个文件必须围绕一个明确、可命名的知识主题，能够回答一组紧密相关的问题。禁止在一个文件中堆积多个无关主题。

可接受的主题：

- “文本分类中宏平均 F1 的定义、计算和适用条件”
- “Label Studio 文本分类任务的项目创建与结果导出”
- “企业数据脱敏流程中的角色、输入、输出和验收证据”

不可接受的主题：

- “人工智能知识大全”
- “本周收集到的资料合集”
- 将课程通知、操作手册、术语表和新闻摘要拼接进同一文件

### 3.2 建议规模

- 本节中的“字符”统一指移除 YAML 元数据头后的 Unicode 字符数量，中文、英文、数字、标点和换行均按字符计数，不按词数或模型 token 数计数。
- 单文件正文建议为 1000 至 8000 个字符。
- 少于 500 个字符时，应确认它是否只是一条可合并的碎片；独立定义、规则或高价值短问答可以例外。
- 超过 15000 个字符时，原则上按子主题、版本、场景或任务阶段拆分。
- 每个主要章节建议为 200 至 1000 个字符；超过 1000 个字符时，应增加具有独立语义的子标题。
- 普通段落建议为 80 至 300 个字符，避免整页只有一个超长段落。

这些长度是召回质量建议，不是系统上传大小限制。系统单文件上限为 50MB，但接近上限的纯文本通常不适合作为一个知识文档。

### 3.3 独立可理解

每个章节和关键段落应在脱离全文后仍能理解：

- 明确重复主题名称，不使用只有上文才能解释的“该方法”“上述规则”“如下图”等指代。
- 说明结论成立的对象、条件、版本、时间或范围。
- 定义缩写第一次出现时的全称和含义。
- 示例必须明确标记为示例，不能伪装成真实事实或真实用户数据。
- 结论与例外应放在同一章节，避免只召回结论而漏掉限制条件。

## 4. 文件、编码与命名规则

### 4.1 编码和换行

- 必须使用 UTF-8 编码。当前解析器会先剥离一个 UTF-8 BOM，因此带 BOM 文件可以解析；为兼容其他检查工具，仍建议保存为无 BOM UTF-8。
- 建议统一使用 LF 换行。
- 禁止出现乱码、不可见控制字符、连续无意义空行或从网页复制的零宽字符。
- 文件必须包含非空正文，不能只有元数据头或标题。
- 文件扩展名必须与内容相符，不得把其他格式仅改名为 `.md` 或 `.txt`。

### 4.2 文件名

文件名建议使用以下结构：

```text
mat_<领域>_<主题>_<版本>_<资料ID>.md
mat_<领域>_<主题>_<版本>_<资料ID>.txt
```

示例：

```text
mat_nlp_macro_f1_v1_0_0_MAT-NLP-001.md
mat_security_data_masking_v2_1_0_MAT-SEC-014.txt
```

文件名规则：

- 使用半角字母、数字、下划线、连字符和点，不使用空格。
- `<领域>` 和 `<主题>` 使用简短、稳定的英文或拼音标识。
- 资料 ID 表示一个长期稳定的逻辑主题，在不同主题之间必须唯一，建议采用 `MAT-<领域>-<三位以上序号>`。
- 同一主题修订时保留资料 ID 并更新版本；物理版本的唯一键为 `(id, version)`，同一组合不得出现两份正文。
- 活跃入库目录中每个资料 ID 只保留一个当前版本；旧版本移入归档区，并通过 `replaces` 记录替代关系。
- 禁止使用 `最终版`、`最新版`、`新建文本文档`、日期堆叠等不可治理名称。

## 5. YAML 元数据头

### 5.1 位置与语法

每个文件必须以扁平 YAML 元数据头开头：

- 移除可选 UTF-8 BOM 后的第一行必须正好是 `---`，前面不能有空行、标题或说明。
- 必须使用另一个单独的 `---` 闭合。
- 每行只写一个 `key: value` 标量。
- 禁止嵌套对象、数组、缩进块、多行值和重复键。
- 值中包含 `#`、首尾空格、`true`、`false` 或 `null` 等容易被通用 YAML 工具改写的内容时，必须使用双引号；URL 中的 `https://` 可以直接书写。
- 元数据值禁止包含换行或未转义的双引号；复杂说明移入批次记录，不塞入元数据头。
- 元数据头闭合后空一行，再开始正文标题。

如果元数据头缺少首行标记或未闭合，元数据可能进入向量正文，或者受控资料包导入会直接失败。

### 5.2 标准字段

```yaml
---
id: MAT-NLP-001
title: 文本分类中宏平均 F1 的计算与适用条件
version: v1.0.0
source: SRC-SKL-METRICS-001
source_refs: SRC-SKL-GUIDE-002
source_type: textbook
license_status: authorized
data_types: text
visibility: student
status: approved
verification_status: verified
language: zh-CN
authoring_method: ai-assisted
created_at: 2026-08-16
updated_at: 2026-08-16
reviewer: reviewer-name
reviewed_at: 2026-08-16
quality_score: 92
review_record: BATCH-20260816-01#MAT-NLP-001@v1.0.0
replaces: MAT-NLP-001@v0.9.0
---
```

字段规则：

| 字段 | 级别 | 规则 |
| --- | --- | --- |
| `id` | 必须 | 逻辑主题 ID，在不同主题之间唯一且跨版本稳定；本地受控资料包导入必填 |
| `title` | 必须 | 准确描述主题，不使用营销式或空泛标题；本地受控资料包导入必填 |
| `version` | 必须 | 推荐 `v主版本.次版本.修订版本`；本地受控资料包导入必填 |
| `source` | 必须 | 指向支撑核心结论的主要来源编号；本地受控资料包导入必填 |
| `source_refs` | 可选 | 其他来源 ID 使用英文逗号分隔的单行标量，例如 `SRC-A-001,SRC-B-002`；禁止 YAML 数组 |
| `source_type` | 必须 | 使用系统允许值；本地受控资料包导入必填 |
| `license_status` | 必须 | 使用系统允许值；未核验时只能写 `pending` |
| `data_types` | 必须 | 本规则固定写 `text` |
| `visibility` | 必须 | 使用系统允许值；本地受控资料包导入必填 |
| `status` | 必须 | 只能使用 `draft`、`reviewed`、`approved`、`deprecated`；它是文件治理状态，不等于数据库发布状态 |
| `verification_status` | 必须 | `pending`、`verified` 或 `conflict`；存在未决事实或来源冲突时不得写 `verified` |
| `language` | 应 | 中文资料使用 `zh-CN`，其他语言使用明确语言标识 |
| `authoring_method` | 应 | `human`、`ai-assisted`、`ai-generated-reviewed` 或 `collected-and-adapted` |
| `created_at` | 应 | `YYYY-MM-DD` |
| `updated_at` | 应 | 每次实质修订后更新 |
| `reviewer` | 审核后必须 | 写实际完成审核的人员或明确角色；未审核草稿必须省略，禁止用 `pending` 伪装审核人 |
| `reviewed_at` | 审核后必须 | 实际完成审核的日期，格式为 `YYYY-MM-DD` |
| `quality_score` | 审核后必须 | 使用第 14.2 节的 0 至 100 整数分值 |
| `review_record` | 审核后必须 | 指向批次逐文件记录，固定格式为 `<批次ID>#<资料ID>@<版本>` |
| `replaces` | 必须 | 被替代版本固定写 `<资料ID>@<版本>`，例如 `MAT-NLP-001@v0.9.0`；首版写 `none` |
| `owner` | 待核验时必须 | 对待核验事项负责的人员或明确角色 |
| `review_due_at` | 待核验时必须 | 复核期限，格式为 `YYYY-MM-DD` |
| `rejection_reason` | 拒收记录必须 | 简短拒收原因；不得复制受限内容或敏感值 |

### 5.3 元数据与上传表单一致性

通过管理端上传时，必须核对文件头与上传表单：

- 标题、版本、来源类型、授权状态、可见范围和数据类型不得冲突。
- 文件夹批量上传会按每个文件名生成数据库标题；来源类型、来源名称、来源 URL、来源台账、版本、授权状态、可见范围、数据类型和能力关联是批次共享字段。
- 同一批次只能选择上述共享字段完全相同的文件。标题可以不同，但文件名主体必须能作为数据库标题；不能满足时应拆批或逐文件上传。
- 文件头为 `pending` 时，禁止在上传表单中填写 `authorized` 来绕过审核。
- 文件头为 `teacher` 时，未经内容审核不得在上传表单中扩大为 `student`。

### 5.4 治理状态与发布资格

文件状态组合必须符合下表。该门禁由资料流程执行，不能因为后端没有读取全部治理字段而省略。

| 文件状态 | 授权状态 | 允许的可见范围 | 处理结果 |
| --- | --- | --- | --- |
| `draft` | `authorized` 或 `internal` | `admin` | 保存在暂存区，不得发布，继续编辑和核验 |
| `reviewed` | `authorized` | `admin` 或 `teacher` | 可以进入批准复核，不得面向学生发布 |
| `reviewed` | `internal` | `admin` 或 `teacher` | 可以内部使用，不得面向学生发布 |
| `approved` | `authorized` | `admin`、`teacher` 或 `student` | 可按目标受众进入入库候选 |
| `approved` | `internal` | `admin` 或 `teacher` | 仅限内部范围，不得设置为 `student` |
| `draft` | `pending` | `admin` | 保存在暂存区，授权完成前不得发布 |
| `deprecated` | `authorized`、`internal` 或 `pending` | `admin` | 保存到归档区，不进入活跃入库目录，由新版本替代 |

状态判定按以下优先级执行，前一条命中后不再套用后续规则：

1. `license_status: forbidden`：拒收，只保存最小拒收记录，原正文不得入库。
2. `status: deprecated` 且授权状态不是 `forbidden`：归档，不进入暂存区或活跃目录。
3. `license_status: pending` 且不是 `deprecated`：`status` 必须为 `draft`、`visibility` 必须为 `admin`，进入待核验区。
4. 其余 `authorized` 或 `internal` 资料按上表的 `draft`、`reviewed`、`approved` 规则处理。

`verification_status` 还必须满足：

- 对非 `deprecated` 的活跃资料，`pending` 或 `conflict`：`status` 必须为 `draft`、`visibility` 必须为 `admin`，进入待核验区；来源冲突未解决时不得扩大到 `teacher`。
- `verified`：可以结合合法授权状态进入 `draft`、`reviewed`、`approved` 或 `deprecated`；是否发布仍由状态表决定。
- `deprecated` 资料按前述状态优先级直接归档，可以保留归档时的历史 `verification_status`，但不得因此返回待核验区或活跃目录。

只有 `status: approved`、`verification_status: verified` 且授权/可见范围组合合法的资料可以进入正式入库候选。

### 5.5 批准、导入与发布责任

正式流程中的责任不得由 AI 自动冒充：

1. 资料编辑者生成或整理文件，完成格式、来源和安全自检，将草稿置于待核验区。
2. 内容审核者对每份资料完成基础人工审核，核验事实、授权、可见范围和检索问题，填写真实审核字段及 `review_record`；审核者不得审核自己无法核验的专业结论。
3. 具有发布权限的系统管理员确认第 5.4 节组合和四道门禁，才可把文件加入正式上传集合或受控 `materials/` 目录并执行导入。
4. 系统管理员观察解析、切片和索引任务全部成功，核对数据库元数据和目标可见范围。要求发布的资料还必须达到数据库 `published` 状态。
5. 系统管理员执行第 14.4 节检索验收。任务失败、状态不符或检索不通过时，资料退回修改；“已上传”不等于“已发布成功”。

只有上述步骤均完成，资料才算正式发布。`admin` 或 `teacher` 范围资料同样必须完成处理任务和检索验收，不能因为未面向学生而跳过质量门禁。

## 6. 来源与授权规则

### 6.1 来源必须可追溯

每份资料至少要能追溯到以下一种来源：

- 官方标准、官方文档、法规或权威机构页面。
- 已明确版本、作者和出版信息的教材或论文。
- 获授权的企业内部制度、教师材料或项目资料。
- 项目原创资料及其事实依据。

AI 不是事实来源。AI 参与生成时，`authoring_method` 应如实记录，`source` 仍应指向支撑内容的原始资料或项目内部依据。

一份资料使用多个来源时，`source` 写支撑核心结论的主要来源，`source_refs` 用英文逗号列出补充来源。每个来源 ID 都必须有独立来源记录，并在正文“来源说明”中写明它具体支撑哪些结论。若多个来源没有共同主题或只是机械拼接，应拆成多份资料。

当前数据库文档元数据只关联一个主要来源台账；`source_refs` 和补充来源的结论映射保存在文件治理记录与正文来源说明中，不会由浏览器上传自动拆成多条数据库来源关联。若业务要求按每个来源独立过滤、撤回或审计，必须按主要来源拆成多份资料，不能依赖 `source_refs` 获得数据库级关联。

### 6.2 来源记录的最小信息

来源记录至少应保存：

- 唯一来源编号，例如 `SRC-OFFICIAL-001`。
- 来源名称、发布方或作者。
- 来源类型和版本或发布日期。
- 原始 URL、DOI、ISBN 或本地归档位置。
- 获取或核验日期。
- 授权状态、许可证或内部授权依据。
- 可使用范围和风险说明。
- 负责核验的人。

网页资料还应记录页面标题和具体章节，不能只保存网站首页地址。

本地受控资料包的来源台账还必须遵循第 16.3 节模板。来源台账 `status` 使用 `approved`、`pending`、`expired` 或 `forbidden`，不要与正文材料的 `license_status` 混用。

### 6.3 授权处理

- `authorized`：已有明确许可、开放许可证或可证明的合法使用依据。
- `internal`：仅限项目内部使用，不得默认扩大到学生公开范围。
- `pending`：授权尚未确认，只能整理和审核，不得发布。
- `forbidden`：明确禁止使用，必须从待入库集合中移除。

禁止通过“AI 改写”掩盖未经授权的大段复制。对受版权保护内容，应提取必要事实、原创解释和短引用，并保留来源；不得批量复刻教材、付费课程、题库或封闭数据库全文。

## 7. 正文结构规则

### 7.1 标题语法

标题必须顶格书写，并在井号后保留一个空格：

```markdown
# 文档主题

## 文档主题：核心定义

### 文档主题：适用条件
```

禁止以下写法：

```text
#没有空格
  ## 带缩进的标题
第一章 核心定义
```

由于当前解析器只保留最近一个标题，标题本身必须具有独立语义。推荐写“宏平均 F1：适用条件”，不写只有上文才能解释的“适用条件”。

### 7.2 推荐章节

知识说明类资料可按以下结构组织：

1. 主题概述：一句话说明解决什么问题。
2. 核心定义：解释术语、对象和边界。
3. 适用条件：说明何时适用、需要什么前提。
4. 操作或计算步骤：提供可执行过程。
5. 示例与反例：展示正确和错误用法。
6. 常见误区：指出容易混淆的概念。
7. 验收或检查方法：说明如何确认结果正确。
8. 限制与待核验事项：保留不确定性和时效边界。
9. 来源说明：列出正文使用的具体来源位置。

并非每份资料都必须机械包含九个章节，但定义、条件、关键步骤、例外和来源不得无故缺失。

### 7.3 段落写法

- 先写结论，再写解释、条件和证据。
- 每段只表达一个主要命题。
- 关键术语在同一资料集中使用同一名称。
- 数字必须带单位，比例必须说明分母，指标必须说明计算口径。
- 日期使用明确时间，例如“截至 2026-08-16”，不写“目前”“最近”。
- 规则变化频繁的内容必须写版本和核验日期。
- 区分事实、建议、推断和示例，不能混写成同等确定的结论。

### 7.4 列表

列表适合表达并列条件、步骤和检查项，但每个列表项必须有明确对象：

- 步骤列表使用有序编号，并说明输入和输出。
- 条件列表应说明满足全部条件还是任一条件。
- 单个列表超过 12 项时，应按主题分组或拆成多个章节。
- 禁止只堆关键词而没有关系、定义或使用条件。

### 7.5 表格

Markdown 表格默认可能作为一个不可拆分的切片，因此：

- 单表建议不超过 6 列、15 行和 500 个字符，绝对不得超过 1000 个字符；字符计算方式与第 3.2 节一致。
- 每个表必须在表前说明用途，在表后总结关键结论。
- 单元格不得塞入长段落、多个步骤或大段代码。
- 大型数据表应拆分，或改写为“字段名：值”的独立句子或列表。
- 重要规则不能只存在于表格中，必须在相邻正文中再次说明。

### 7.6 代码和命令

- 代码块必须标明语言。
- 代码前说明用途、适用环境和前置条件，代码后说明预期结果。
- 示例不得包含真实密码、令牌、私钥、Cookie、连接串或个人信息。
- 省略部分必须明确标记，不能让读者误以为示例可直接运行。
- 与知识主题无关的大段源代码应链接或归档，不应整段塞入 RAG 正文。

### 7.7 图片、附件和外链

本规则的正文格式不能直接承载图片语义。资料引用图片、视频、音频或附件时：

- 必须在正文中写出理解结论所需的文字描述。
- 禁止使用“见下图”代替关键事实。
- 外链只能作为证据入口，正文仍要包含可检索的必要信息。
- 链接失效不会自动更新资料，因此应记录核验日期和替代来源。

## 8. 面向切片和检索的写作规则

### 8.1 一个切片表达一个知识单元

每个 200 至 600 个字符左右的知识单元应包含：

- 明确主题或实体名称。
- 一个主要结论。
- 结论成立的条件或范围。
- 必要解释、步骤或短例子。
- 重要例外或风险。

不要为迎合长度机械截断句子。章节较长时，应在自然语义边界增加子标题。

### 8.2 标题必须带检索词

标题应包含用户可能查询的名词、指标、工具或任务，不使用文学化标题。

推荐：

- `## 宏平均 F1：计算步骤`
- `## 数据脱敏：发布前检查`
- `## Label Studio 文本分类：导出结果`

不推荐：

- `## 深入理解`
- `## 更多内容`
- `## 第二步`

### 8.3 问答覆盖

资料应自然覆盖真实问题的不同表达，但禁止关键词堆砌。可以在正文或“常见问题”章节回答：

- “是什么”类定义问题。
- “为什么”类原理问题。
- “怎么做”类步骤问题。
- “什么时候用”类条件问题。
- “为什么失败”类诊断问题。
- “A 和 B 有什么区别”类比较问题。

同一答案不应复制到多个文件。应保留一份权威正文，其他资料通过明确主题关系引用它。

### 8.4 正反例必须完整

反例必须指出错误点和修正方式。仅写“错误示例”而不说明为什么错误，对检索回答帮助有限。

示例数据必须使用明显虚构值，例如 `user@example.test`、`13800000000`，并在正文中注明“虚构示例”。不要使用看似真实的身份证号码。

## 9. AI 生成资料规则

### 9.1 输入要求

交给 AI 生成资料前，至少提供：

- 主题、目标读者和使用场景。
- 允许使用的来源内容或来源链接。
- 需要覆盖和禁止扩展的范围。
- 资料 ID、来源 ID、版本、授权状态和可见范围。
- 需要回答的典型问题。
- 专业术语、产品版本和时间边界。

缺少事实来源时，AI 只能整理通用框架、待核验问题或明确标记的示例，不能自行补造具体事实、统计数字、法规条文、引用、URL 或版本号。

### 9.2 输出要求

AI 必须：

- 只输出一份完整文件内容，不附加对话式前言或总结。
- 严格使用指定的 YAML 标量字段和标题结构。
- 保留来源中的条件、例外、版本和不确定性。
- 用自己的组织和解释表达内容，不进行同义替换式洗稿。
- 将推断标为“推断”或“建议”，将虚构内容标为“示例”。
- 对无法核验的内容写“待核验”，不得用流畅语言掩盖证据缺口。
- 在末尾列出实际使用的来源及具体章节或页面。

AI 禁止：

- 编造来源、作者、发布日期、许可证、统计数字和实验结果。
- 把搜索摘要、论坛回答或 AI 旧知识当成已核验事实。
- 删除原资料中的限制条件，使结论显得更绝对。
- 生成真实个人信息、账号凭据或内部敏感数据。
- 为凑长度重复定义、结论或例子。

## 10. 收集与整理现有资料规则

### 10.1 收集前判断

收集者必须先判断：

1. 资料是否与知识库目标和用户问题相关。
2. 来源是否可靠，版本是否明确，内容是否仍然有效。
3. 是否有权复制、改写、引用和向目标用户展示。
4. 是否包含个人信息、内部信息、商业秘密或安全凭据。
5. 是否已经存在相同或更权威的资料。

任一关键问题无法判断时，资料进入待核验区，不得直接作为已批准正文入库。

仓库内资料使用以下固定工作区；这些目录是治理约定，本任务不会自动创建它们：

- 受控包待核验：`docs/ragData/_staging/pending/controlled/`。
- 浏览器上传待核验：`docs/ragData/_staging/pending/browser/`。
- 最小拒收记录：`docs/ragData/_staging/rejected/`。
- 历史版本归档：`docs/ragData/_archive/materials/<资料ID>/<版本>/`。

待核验目录不在当前本地资料包导入范围内，也不得与浏览器已批准上传集合混用。待核验文件必须填写 `owner` 和 `review_due_at`。完成核验后，更新 `verification_status`、`status`、真实审核字段与版本，再移入活跃 `materials/` 或上传集合；确认禁止使用时，只在拒收目录保存包含资料 ID、来源 ID、日期、责任人和 `rejection_reason` 的最小记录，并删除不必要的受限原文。

### 10.2 清洗步骤

按以下顺序处理收集资料：

1. 保存来源信息和原始版本的校验值或归档位置。
2. 删除导航、广告、页眉页脚、评论区、推荐阅读和无意义版权模板等噪声。
3. 修复断行、乱码、错误空格、重复页和 OCR 常见错误。
4. 保留标题、列表、步骤、表格、代码和警告之间的语义关系。
5. 按单一主题重组文件，不按原网页分页机械切分。
6. 对事实、版本、数字、单位、链接和授权信息进行核验。
7. 补充独立可理解的标题、条件、例外和来源说明。
8. 执行去重、敏感信息检查和人工复核。

清洗不能改变原意。若需要加入项目建议，应单独标记为“项目建议”，不能伪装成来源原文。

## 11. 事实质量与冲突处理

### 11.1 事实核验

以下内容必须逐项核验：

- 法规、标准、政策、版本和生效日期。
- 数字、公式、单位、阈值、性能结果和统计口径。
- API、配置项、命令、界面路径和产品行为。
- 引用、作者、出版信息、URL、许可证和授权声明。
- 对学生产生评价、操作或安全影响的结论。

“看起来合理”不等于已核验。核验记录应包含依据、日期和核验人。

### 11.2 冲突资料

两个来源冲突时：

- 不得静默拼接成一个折中结论。
- 优先核对版本、发布日期、适用地区、产品版本和定义口径。
- 在正文中明确分别说明两个结论及各自条件。
- 无法解决时标记“存在来源冲突，待确认”，并限制可见范围。
- 后续确认权威结论时更新版本，不覆盖旧版本的审计记录。

### 11.3 时效性

- 稳定概念至少每年复核一次。
- 产品操作、接口、价格、政策和法规应根据变化频率缩短复核周期。
- 已确认失效的资料标记 `deprecated`，从可发布批次移除，并保留替代资料 ID。
- 禁止仅修改日期而不重新核验正文。

## 12. 去重与版本管理

### 12.1 去重层级

入库前至少执行三层去重：

1. 文件级：比较文件校验值，发现完全相同文件。
2. 标题与主题级：规范化标题、来源和版本，发现改名重复。
3. 内容级：比较正文相似度，人工确认同义改写、拼接重复和新旧版本。

高相似资料的处理方式：

- 同一来源同一版本：保留一份权威文件。
- 同一主题不同来源：保留各自独有证据和视角，删除重复背景。
- 同一资料不同版本：使用相同逻辑资料 ID，以 `(id, version)` 区分物理版本，明确替代状态；活跃入库目录只保留当前版本。
- 仅增加无关段落或措辞变化：不作为新版本入库。

### 12.2 版本规则

推荐使用 `v主版本.次版本.修订版本`：

- 主版本：主题边界、核心结论或适用对象发生重大变化。
- 次版本：增加新的已核验章节、场景或来源。
- 修订版本：纠错、链接更新、表述澄清或小范围数据修正。

每次版本更新应记录变更原因、核验范围和替代关系。禁止删除旧版本后假装资料从未变化。

旧版本应放入 `docs/ragData/_archive/materials/<资料ID>/<版本>/`，该目录不参与活跃导入。当前版本的 `replaces` 使用 `<资料ID>@<版本>` 指向被替代版本，例如 `MAT-NLP-001@v1.2.0`；首个版本写 `replaces: none`。批次记录同时保存变更原因，工具可以按 `@` 左右两部分解析替代链。

## 13. 隐私、安全与内容边界

### 13.1 禁止内容

资料不得包含：

- 真实身份证号、手机号、个人邮箱、住址、学号等非必要个人信息。
- 密码、API Key、访问令牌、私钥、Cookie、验证码或数据库连接凭据。
- 未脱敏的学生作业、聊天记录、客户数据、日志和工单。
- 商业秘密、受限内部信息或超出授权范围的内容。
- 恶意指令、绕过权限的方法或会直接造成现实风险的操作细节，除非任务明确需要且经过授权和安全评审。

当前系统会扫描手机号、身份证号和邮箱，其中身份证号命中会阻止发布。但系统扫描只是最低防线，不能替代人工隐私审查，也不会自动发现所有敏感信息。

### 13.2 脱敏规则

- 优先删除非必要字段，而不是简单替换部分字符。
- 必须保留结构时，使用明显虚构且不可还原的值。
- 脱敏后重新检查上下文，避免通过姓名、单位、时间和事件组合重新识别个人。
- 脱敏记录应说明处理范围，但不得在记录中保存原始敏感值。

## 14. 审核和验收流程

### 14.1 四道门禁

每份资料依次通过：

1. 格式门禁：扩展名、UTF-8、YAML 头、标题、非空正文和文件名合格。
2. 治理门禁：来源、版本、授权、可见范围、去重和审核责任明确。
3. 内容门禁：事实准确、范围完整、章节自包含、无冲突和无重复填充。
4. 检索门禁：切片可读，典型问题能够召回正确章节，回答不会遗漏关键限制。

任一硬门禁失败，资料退回修改，不得用总分抵消授权、安全或事实错误。

逐文件审核声明记录在 YAML 头的 `verification_status`、`reviewer`、`reviewed_at`、`quality_score` 和 `review_record` 字段中。`review_record` 必须能定位到第 18 节批次记录中的唯一逐文件行；该行关联核验依据、缺陷、检索问题及结果，形成证据链。未完成审核的草稿不得提前填写审核人、质量分或审核记录引用。

### 14.2 质量评分

| 维度 | 分值 | 判断重点 |
| --- | ---: | --- |
| 来源与可追溯性 | 20 | 来源具体、版本明确、引用位置可核验 |
| 事实准确性 | 20 | 数字、条件、例外、时效和术语正确 |
| 结构与可读性 | 15 | 标题具体、层次清晰、段落单一主题 |
| 切片独立性 | 15 | 单个章节或切片脱离全文仍能理解 |
| 问题覆盖 | 10 | 能回答目标用户的定义、步骤、条件和诊断问题 |
| 一致性与去重 | 10 | 无自相矛盾、无重复填充、版本关系清楚 |
| 授权、隐私与安全 | 10 | 授权合格，无敏感信息和越权内容 |

评分结果：

- 85 至 100 分：可以进入入库候选。
- 70 至 84 分：修订后重新审核。
- 低于 70 分：拒收或重新制作。
- 存在禁止发布的授权、隐私、安全或重大事实问题：无论总分多少都拒收。

### 14.3 批次抽检

- 第 5.5 节的逐文件基础人工审核覆盖 100% 正式候选；本节抽检是由第二审核者执行的额外深度复核，不能替代逐文件基础审核，也不能为未查看内容的文件填写审核人或质量分。
- 格式、元数据、重复和敏感信息检查必须覆盖 100% 文件。
- 新来源、新 AI 提示词或新整理流程的首批资料应进行 100% 第二人深度复核。
- 流程稳定后，普通批次第二人深度复核的基础抽检数为 `K = min(批次总数, max(20, ceil(批次总数 × 20%)))`。
- 为跨工具复现基础样本，对每个文件计算 `SHA-256(UTF-8(<批次ID> + "\n" + <文件名>))`，按十六进制摘要升序排列并取前 K 个。最终样本是“基础样本、高风险文件、自动检查告警文件”的集合并集，按文件名去重，因此最终数量可以大于 K。
- 法规、标准、安全、评价规则和直接面向学生的高风险资料必须 100% 第二人深度复核。
- 同一种缺陷在两个抽检文件中出现，或影响至少 10% 的抽检文件时，视为系统性问题并扩大到全批次复核，不得只修被抽中的文件。

100% 自动检查至少包括：

- UTF-8、首行元数据头、必填字段、枚举、标题语法、非空正文和长度。
- 文件校验值精确去重，以及规范化 `(id, version)` 唯一性。
- 在固定嵌入模型下，正文相似度不低于 0.92 的文件作为重复候选拒绝自动入库；0.80 至 0.92 进入人工复核。阈值调整必须记录模型、评测结果和规则版本。
- 手机号、身份证号、邮箱、密钥和凭据模式扫描。自动扫描未命中仍必须接受人工安全审查。

### 14.4 检索验收

每个主题至少准备以下测试问题：

- 一个直接定义或事实问题。
- 一个带条件的操作或判断问题。
- 一个反例、误区或失败诊断问题。

存在被替代版本时，每个相关主题还必须增加一个版本辨别问题，确认归档旧版不在活跃语料中且不会压过当前版本。每个批次另准备 `max(3, ceil(批次资料数 ÷ 20))` 个无答案问题，覆盖批次主要领域；预期结果是没有不相关资料越过活动分数阈值，且启用回答生成时执行拒答策略而不编造结论。

验收必须冻结并记录嵌入模型、检索设置、过滤条件和资料版本。未单独批准参数时使用当前基线：`top_k=5`、`score_threshold=0.35`、混合检索开启、重排关闭。

每个测试问题必须分配唯一问题 ID，并在执行前记录问题类型、预期资料 ID、预期章节和预期行为。通过条件是：预期当前版本资料及目标章节进入返回的前 5 个结果，且命中切片同时包含回答所需的核心结论和限制条件。每份资料的三个必测问题及适用的版本辨别问题必须全部通过；任一问题失败，该资料退回修订，不随批次其他合格资料入库。无答案问题全部通过才允许批次发布。不同模型或参数下的结果不得直接混合比较。

同时确认：

- 召回切片包含答案所需的条件和例外。
- 相似但错误版本不会压过当前权威版本。
- 仅凭召回切片也能识别来源、主题和适用范围。
- 无答案问题不会被资料中的模糊语句误导为确定答案。

## 15. 入库前检查清单

### 15.1 文件检查

- [ ] 文件为 `.md` 或 `.txt`，并符合所选入库方式。
- [ ] UTF-8 编码、无乱码、无异常控制字符。
- [ ] 文件名可治理，资料 ID 唯一。
- [ ] 第一行是 `---`，元数据头正确闭合。
- [ ] 元数据头之后存在非空正文。
- [ ] 所有标题顶格书写，并使用 `# ` 至 `###### `。

### 15.2 元数据检查

- [ ] `id`、`title`、`version`、`source`、`source_type`、`license_status`、`data_types`、`visibility`、`status`、`verification_status` 完整。
- [ ] 系统枚举值合法，`data_types` 为 `text`。
- [ ] `(id, version)` 唯一，活跃目录中该 ID 只有一个当前版本，替代旧版时已填写 `replaces`。
- [ ] `source_refs` 如存在则为英文逗号分隔标量，且每个来源记录均存在。
- [ ] 来源记录存在，版本、URL 或归档位置可核验。
- [ ] 文件头与上传表单元数据一致。
- [ ] 文件状态、核验状态、授权状态和可见范围组合符合第 5.4 节。
- [ ] 待核验资料填写 `owner` 和 `review_due_at`；已审核资料填写 `review_record` 并能关联到批次逐文件记录。

### 15.3 内容检查

- [ ] 单文档单主题，标题准确。
- [ ] 关键章节包含对象、条件、结论、例外和必要证据。
- [ ] 事实、建议、推断和示例已经区分。
- [ ] 数字、单位、日期、版本和链接已经核验。
- [ ] 无关键词堆砌、重复段落、导航广告和无关内容。
- [ ] 大型表格和超长章节已经拆分。
- [ ] 无依赖上文才能理解的模糊指代。

### 15.4 治理与安全检查

- [ ] 已完成文件、标题和内容三层去重。
- [ ] 无真实个人信息、凭据和未经授权的内部信息。
- [ ] 无未经许可的大段复制或受限全文。
- [ ] AI 参与方式如实记录，AI 未被当作事实来源。
- [ ] 已批准资料记录了真实审核人、审核日期、质量分和明确核验结论，且没有未决待核验项；草稿未伪造审核字段。
- [ ] 固定检索配置已经记录，三个必测问题全部通过。

```markdown

source: SRC-DOMAIN-001
source_type: other
license_status: pending
data_types: text
visibility: admin
status: draft
verification_status: pending
language: zh-CN
authoring_method: ai-assisted
created_at: 2026-08-16
updated_at: 2026-08-16
owner: content-reviewer
review_due_at: 2026-08-23
replaces: none
---

# 具体主题名称

用一段话说明本资料解决的问题、适用对象、范围和版本边界。

## 具体主题名称：核心定义

先给出准确结论，再解释术语、对象和必要背景。

## 具体主题名称：适用条件与限制

说明何时适用、何时不适用、需要哪些前提以及有哪些例外。

## 具体主题名称：操作步骤

1. 写明输入和前置条件。
2. 写明关键处理动作。
3. 写明输出和验收证据。

## 具体主题名称：示例与反例

提供一个明确标记的虚构示例，再说明一个反例为什么错误以及如何修正。

## 具体主题名称：常见问题

### 具体主题名称：问题一

直接回答问题，并保留条件和例外。

## 具体主题名称：来源说明

- 来源：来源名称，具体章节或页面，版本，URL 或归档位置，核验日期。
- 待核验：没有则写“无”。
```

### 16.3 本地受控资料包的来源台账模板

只有仓库内受控资料包需要按此模板创建 `docs/ragData/sources/SRC-*.md`。文件名使用 `SRC-<领域>-<序号>__<简短主题>.md`，其中前半部分必须与 `source_id` 完全一致；`source_id` 在来源集合中唯一。来源台账至少包含 `source_id`、`title`、`category` 和 `status`，其他字段按来源实际情况填写。

来源台账的 `status` 使用 `approved`、`pending`、`expired` 或 `forbidden`，它与正文材料的 `license_status` 是两个不同字段。只有经过实际授权核验的来源才能写 `approved`；`pending`、`expired` 或 `forbidden` 来源不能支撑 `license_status: authorized` 的正式材料。

```markdown
---
source_id: SRC-DOMAIN-001
title: 来源名称
issued_by: 发布方或作者
category: other
version: 2026-08
status: pending
url: https://example.test/source
valid_from: 2026-08-16
valid_to: 2027-08-16
risk: 授权、时效或适用范围说明
owner: source-reviewer
review_due_at: 2026-08-23
---

# 来源台账：来源名称

## 来源台账：核验范围

说明实际核验的页面、章节、版本和事实范围，不把网站首页可访问等同于全文已经核验。

## 来源台账：授权依据

说明许可证、书面授权、内部批准或仅允许引用的边界。未完成核验时保留 `status: pending`。

## 来源台账：风险与复核

记录已知风险、责任人、核验日期和下一次复核日期，不记录任何凭据或受限原文。
```

## 17. 合格与不合格示例

### 17.1 合格片段

```markdown
## 宏平均 F1：适用条件

宏平均 F1 先分别计算每个类别的 F1，再对所有类别取算术平均，因此每个类别拥有相同权重。它适合需要同等关注少数类和多数类的多分类任务。若业务更关注样本总体表现，或类别重要性并不相同，应同时查看微平均 F1、加权 F1 和各类别指标，不能只依据宏平均 F1 作结论。
```

该片段主题明确，包含定义、适用条件和限制，即使单独召回也能理解。

### 17.2 不合格片段

```text
## 适用条件

这个指标很好，很多时候都可以使用。具体计算方法见上文，其他情况需要根据实际需求灵活处理。
```

问题包括：标题缺少主题词；“这个指标”“见上文”依赖上下文；“很多时候”“灵活处理”没有可判断条件；没有说明限制和证据。

## 18. 批次交付记录

每次交付一批资料时，应附一份批次记录，至少包括：

- 批次编号、生成或收集日期、负责人。
- 文件数量、主题范围、来源范围和可见范围。
- 使用的 AI 模型、提示词版本或人工整理流程版本。
- 自动检查规则版本、相似度模型和阈值、抽样哈希输入、基础/深度人工审核比例和不合格数量。
- 去重结果、敏感信息检查结果和授权状态分布。
- 检索模型、`top_k`、分数阈值、混合/重排设置、测试问题数量、通过率和主要失败类型。
- 已知限制、待核验事项和下一次复核日期。

批次记录用于证明资料如何产生和如何通过门禁，不应包含密码、密钥、个人信息或受限原文。

### 18.1 批次级记录格式

每个批次使用一个 `.md` 记录，文件名为 `BATCH-<YYYYMMDD>-<两位序号>.md`。文件必须写明批次 ID、规则版本、文件清单校验值、自动检查工具/版本、哈希抽样输入与最终样本、检索配置、负责人、发布操作人、发布完成时间和最终决定。该算法不使用随机数，因此不得另填“随机种子”。

抽样记录至少保存：按文件名排序的候选清单、每个文件的抽样 SHA-256、基础 K 值、基础样本、高风险/告警增补样本和去重后的最终样本。这样其他工具无需依赖特定随机数库即可复算。

### 18.2 逐文件证据格式

批次记录必须为每个文件建立唯一记录键 `<批次ID>#<资料ID>@<版本>`，并与正文 YAML 的 `review_record` 完全一致。每条记录至少包含：

| 字段 | 内容 |
| --- | --- |
| 记录键 | `<批次ID>#<资料ID>@<版本>` |
| 文件与校验值 | 文件名、SHA-256、正文字符数 |
| 来源证据 | 主要/补充来源 ID、具体章节或页面、核验日期 |
| 自动检查 | 格式、枚举、去重、相似度、敏感信息结果 |
| 人工审核 | 审核人、审核日期、质量分、发现的问题与处理 |
| 检索问题 | 问题 ID、类型、预期章节、实际 TopK、是否通过 |
| 处理任务 | 数据库文档 ID，解析/切片/索引任务 ID、最终状态和完成时间 |
| 发布结果 | 数据库文档状态、实际可见范围、`published_at`、发布操作人和完成时间；未发布时写失败阶段与原因 |
| 检索运行 | 验收运行 ID、冻结配置、执行时间和最终通过/失败结果 |
| 状态决定 | 已发布、仅内部发布、退回、待核验、拒收或归档及原因 |
| 版本关系 | `replaces`、变更原因和旧版归档位置 |

批准资料的逐文件记录不得省略失败后修订的历史。只有处理任务成功、要求发布的资料达到数据库 `published` 状态且检索运行通过后，状态决定才能写“已发布”或“仅内部发布”。较长证据可以引用受控归档位置，但引用必须可访问、版本固定且不包含不必要的敏感内容。

## 19. 最终原则

1. 数量不能替代质量；错误、重复或无来源资料会直接降低检索结果。
2. AI 可以提高整理效率，但不能替代来源、授权和事实责任。
3. 每个切片都应能回答一个明确问题，并保留答案成立的条件。
4. 无法核验的内容必须显式标记，不得包装成确定事实。
5. 资料入库只是开始；应根据真实查询、召回失败和来源更新持续修订。
